P1 sits on botopink-lang branch `front/b162-p1` (not pushed; I can push it as a branch for you to read). std's `context.bp`
has the opaque `Scope` (`root`, `childAt`, `close`, `detach`), `Place`, `resolve<T>(c, scope, key) -> T | Async<T>` and
`pub async fn run<T>(c: Component<T>, scope: ?Scope = null) -> Async<T>`. A component body lowers to
`{ bpScope__, bpKey__ -> val cell = enter(scope, key); … }`. Every component cell (~60) is red on wasm, for three reasons:

1. std's `context` falls back from GC to linear because the wasi cell helpers (`CellNew` / `CellGet` / `CellSet` / `CellFilled`,
   `memo_cell`) have no GC form.
2. In linear mode `is Async<unknown>` has no run-time test, because tasks carry no descriptor. `run` reads that test (823). Your
   `ref.test (ref $task)` covers GC mode only.
3. `run<T>` / `resolve<T>` are not monomorphised from a component argument, because a lowered component fn answers
   `fn(unknown, unknown) -> unknown`. Boxing `T` into `T | Async<T>` inside `resolve` traps.

The old model ran on wasm only because `lowerRun` read the closure mark. My thread named two ways out: GC forms for the cell helpers
plus a component fn typed `fn(unknown, unknown) -> R`, or a mark-aware call of a `Composition`-typed value in linear mode.
Which one is 164's, and when? P1 lands only when wasm is green; until then its other pieces (P3 folded in, 884, 888, the cells) go on
on the branch. It touches `primitives.bp`, std's `context.bp` and the wasm `run` lowering.
