- **766 (50-b, the maintainer: "somente a (a)")**, meta cd3b95477. `rakun-ssr dev` is `build` then `start` looped over a file watcher
  (std's `fs` mtimes over `src/`, `public/`, `rakun-ssr.json`, `botopink.json`; the child spawned with `forwardSignals`): the node
  restarts on every change and serves the bytes `start` serves. Hot-loading is not a form of the loop on any target — a fable plan
  measured it: the server exists on erlang alone (rakun erlang-only, no listener on node or wasm), so a reload is a restart on
  commonJS and wasm by construction; on the BEAM a swap leaves state `start` never has (`persistent_term` `val` caches, ETS
  `var`s, the append-only UI table, 665's registry, the build id read once) and an init order 580/660 never produce. Island
  state is lost on every edit. **Machine 1 (150 steps-onze step 2, 53 step 6):** the boxes are in `steps-onze.md`, with 50-g
  (`serverMainSource` still writes `@TypeInfo.all` and `onze_routes.routeModules()` — rewrite to 665's registry read; the
  generated route table stays, the import role goes).
- **767 (50-c, the coordinator †)**: `botopink build` materialises the dependencies' cached `.beam` into the output (509 (4), as
  `run` does) and rakun-ssr's `compileBeam` runs `erlc` only over the `.erl` with no `.beam` beside them — today it recompiles
  ~4,000 dependency modules on every build. **Machine 2 (B-57):** the materialisation in `build`, cell
  `build_materialises_dependency_beams`; **machine 1:** `compileBeam`'s narrowing once it lands.
